4. CO Z PŮVODNÍHO AUDITU ZŮSTÁVÁ PLATNÉ

Hlavní architektonický závěr:

Cockpit je funkční a má silnou testovací základnu, ale app/cockpit.py stále
koncentruje příliš mnoho odpovědností. Správným směrem není přepis od nuly,
plošné mazání ani změna frameworku. Správným směrem jsou malé
behavior-preserving řezy při zachování URL, payloadů, potvrzovacích hranic,
private cest a uživatelského chování.

Původní rizikové oblasti:

- HTTP infrastruktura, routing, HTML, CSS a JavaScript v jednom souboru,
- dokumentové a e-mailové orchestrace uvnitř Cockpitu,
- široký dopad každé změny na plnou Cockpit Quality Gate,
- historická směs aktuálních a překonaných stavů v projektové paměti,
- vícekrokové dokumentové a e-mailové workflow s vysokými nároky na recovery.

Kanonická pravidla dalšího vývoje:

1. Nová větší business logika nevzniká v app/cockpit.py.
2. Cockpit dostává pouze tenký adaptér, registraci nebo kompatibilní routu.
3. Jeden krok řeší jednu odpovědnost.
4. Backendová extrakce se nemíchá s UI redesignem, datovou migrací ani legacy
   cleanupem.
5. Každý nový modul má malou přímou regresní sadu.
6. Plná Cockpit Quality Gate zůstává release pojistkou.
7. Po potvrzeném nasazení následuje smoke test 5/5.
8. Počet řádků je orientační metrika, ne důvod k mazání funkčnosti nebo testů.


5. CO JE Z PŮVODNÍHO AUDITU UZAVŘENÉ

Následující body se nesmějí vracet jako nové úkoly bez čerstvého důkazu
regrese:

- lehký /api/live-status je oddělený od plného /api/status,
- krátký live refresh nepřekresluje celý dashboard,
- lokální a vzdálený přístup používají jednu Python instanci Cockpitu,
- Tailscale cesta vede k téže instanci,
- centrální HTTP ochrana řeší limity těla, chybný JSON, Content-Type, Host,
  Origin/Referer, obecné chyby a bezpečnostní hlavičky,
- provozní chybový log neukládá soukromé payloady,
- POST registry a potvrzovací hranice jsou pokryté testy,
- e-mailový work model, repository základ, decision adapter, idempotency a
  nedestruktivní auditní pilot jsou hotové,
- stará aktivní komunikační větev VoiceBridge/Janička je vyřazená,
- Human-Adam a kanonické pracovní proudy fungují,
- R2-Adam už není návrh před implementací: má vlastní chat, TXT prostor,
  dokumentovou lištu, čtečku a potvrzovanou práci s úplnými sadami zdrojů,
- Rodinný kalendář má implementovanou potvrzovanou aktivační bránu; jeho
  aktuální živý režim se před další akcí musí ověřit read-only,
- recovery záloha je aktuální.

Původní doporučení „nejdřív live status + jedna instance + základní HTTP
ochrany“ je historicky splněné a není současnou roadmapou.

7. SMĚR 1 - COCKPIT DIETA

Proč je první:

- app/cockpit.py má po D1 a D2 při měření 30. 7. 2026 10 048 fyzických a
  9 375 neprázdných řádků,
- hlavní systémové riziko je koncentrace odpovědností, ne jedna konkrétní chyba,
- menší moduly zrychlí vývoj, testování, diagnostiku i bezpečné nasazení všech
  dalších oblastí.

Dieta D0 - pouze read-only mapa:

1. Znovu změřit současný app/cockpit.py.
2. Zmapovat:
   - HTTP infrastrukturu a společné odpovědi,
   - registry a tenké adaptéry,
   - business logiku,
   - vložené HTML, CSS a JavaScript,
   - dokumentové routy a služby,
   - e-mailové routy a služby,
   - servisní a procesní operace.
3. U e-mailové oblasti vytvořit call-site mapu od routy přes službu až k modelu
   a repository.
4. Oddělit skutečné adaptéry od business logiky, která patří mimo monolit.
5. Vybrat právě jednu soudržnou e-mailovou skupinu pro D1.
6. Zapsat závislosti, potvrzovací hranice, přímé testy a rizika vybraného řezu.

D0 nesmí:

- měnit kód,
- přesouvat soubory,
- měnit endpointy nebo payloady,
- číst private obsah,
- dělat e-mailové nebo dokumentové zápisy,
- spouštět reindex,
- čistit legacy kód,
- redesignovat UI,
- nasazovat.

Výstup D0:

- stručný git-safe report mapy odpovědností,
- jediný doporučený D1 řez,
- přesný seznam produkčních a testovacích souborů,
- seznam zachovávaných URL, payloadů a potvrzovacích hranic,
- nejmenší implementační krok.

Dieta D1 - jeden e-mailový řez:

- vyjmout pouze skupinu vybranou v D0,
- použít existující work model a repository, pokud jsou pro skupinu vhodné,
- v app/cockpit.py ponechat tenké kompatibilní adaptéry,
- zachovat send/delete/archive potvrzení a private hranice,
- přidat přímé testy nového modulu,
- spustit cílené testy, plnou gate a po samostatně potvrzeném nasazení smoke
  test 5/5.

Dieta D2 - frontend:

- až po stabilizaci backendových hranic přesouvat HTML, CSS a JavaScript do
  samostatných statických souborů,
- nedělat při tom redesign hlavní obrazovky.

Dieta D3 - rychlejší zpětná vazba:

- udržovat malé doménové testovací sady,
- plnou gate zatím neoslabovat,
- zmenšení release gate řešit až po samostatném důkazu bezpečnosti.

Cockpit Dieta D0-D3 je uzavřená a nasazená. Další dietní řez se nemá otevírat
uvnitř následujícího provozního směru bez nového konkrétního důvodu.


8. SMĚR 2 - PRAVDIVÁ PAMĚŤ A RAG

Problém:

Agregovaná paměť může zaostávat za TVBCP, handoffem a živým stavem. Při této
revizi například ACTIVE_PROJECTS.md stále uváděl R2-Adama jako projekt před
implementací a Rodinný kalendář před aktivační bránou, přestože novější
kanonické zdroje dokládají další vývoj. Takový drift vede Adama i systémový
audit ke špatným doporučením.

Cíl:

- jeden současný stav nesmí být přebíjen starším snapshotem,
- historická paměť zůstane zachovaná, ale nebude řídit dnešní práci,
- Samantha musí umět dohledat nejnovější kanonický zdroj bez embeddings.

Nejmenší bezpečný postup:

1. Udělat read-only audit 30 pracovních proudů.
2. U každého porovnat agregovaný registr s nejnovějším TVBCP/handoffem.
3. Označit pouze prokazatelné rozpory, ne domněnky.
4. Opravit nejdřív proudy, které ovlivňují současnou roadmapu:
   - Cockpit,
   - Human-Adam,
   - R2-Adam,
   - Rodinný kalendář,
   - Dokumenty,
   - E-mail,
   - Automatické úkoly.
5. Zachovat staré handoffy jako historii, ale odebrat jim aktivní navigační
   autoritu, pokud jsou překryté.
6. Provest praktické dotazy přes Samanthu a ověřit, že sama volí vhodný
   source_type a vrací současný zdroj.

Co nyní nedělat:

- nezavádět embeddings před praktickým testem současného textového hledání,
- nemazat staré handoffy bez přesného seznamu a potvrzení,
- nepřepisovat historii TVBCP,
- nevytvářet další paralelní registr.


9. SMĚR 3 - E-MAIL -> PRIVATE VAULT -> R2 TXT

Proč:

Samantha má mnoho hotových dílů, ale největší hodnotu prokáže jejich jediný
úplný reálný průchod. Tento test současně ověří Cockpit, e-mailový intake,
dokumentový vault, ScanDocu Review, metadata, hledání a R2-Adama.

Jeden kontrolovaný scénář:

1. V Cockpitu vybrat jeden konkrétní reálný e-mail s PDF a JPEG přílohou.
2. Read-only ověřit náhled a kandidáty.
3. Po příslušném potvrzení uložit vybrané přílohy do private vaultu.
4. V ScanDocu Review doplnit a potvrdit metadata.
5. Ověřit, že se již zrevidovaný dokument nevrací do chybné fronty.
6. Přes R2-Adama provést metadata-only hledání.
7. Ukázat redigované kandidáty a vyžádat potvrzení přesného výběru.
8. Vytvořit nový create-only TXT přehled v prostoru R2.
9. Otevřít TXT v samostatné čtečce.

Bezpečnost:

- soukromý obsah se nevypisuje do chatu, Gitu, paměti ani TVBCP,
- zdrojové dokumenty R2 pouze čte,
- nejasný document_id nebo neúplná sada selže uzavřeně,
- „všechny dokumenty“ znamená úplnou potvrzenou sadu,
- dávky mají nejvýše pět zdrojů,
- chybějící hodnoty zůstávají „nezjištěno“,
- TXT vzniká create-only a nepřepisuje existující dokument.

OCR obrazkových příloh se do tohoto testu nepřidává jako vedlejší vývoj. Pokud
průchod odkryje OCR potřebu, vznikne samostatný návrh.

6. Otevřít TXT z dokumentové lišty v samostatné čtečce.

14. POSLEDNÍ ÚKOL ROADMAPY - OPRAVA GENERÁTORU SYSTÉMOVÉHO AUDITU

Proč současný generátor nepomáhá:

Dnešní nově vygenerovaný systémový audit použil zastaralé řádky
ACTIVE_PROJECTS.md jako současnou pravdu. Výsledkem bylo zejména:

- doporučení starého kroku Rodinného kalendáře, přestože novější TVBCP a
  provozní důkazy popisují další stav,
- tvrzení, že R2-Adam je před implementací, přestože má funkční chat,
  dokumentovou lištu, čtečku a dokumentové workflow,
- klasifikace čistého main napřed o 16 commitů jako potřeby „oddělit hotové a
  rozpracované změny“,
- mechanická volba prvního řádku priority 1 místo skutečné strategické volby,
- surový počet všech výskytů [PRIPOMENOUT] bez rozlišení aktivní a historické
  navigace,
- dlouhý seznam projektů místo krátkého rozhodovacího itineráře,
- míchání provozních předpokladů, hotové údržby a strategických směrů.

Kořen problému v implementaci:

- app/project_audit_report.py čte jako hlavní projektový zdroj
  ACTIVE_PROJECTS.md,
- _prioritize_items řadí převážně podle číselné priority a pořadí tabulky,
- _quick_recommendations vybírá priority_1[0],
- každý výskyt slova „ahead“ spouští doporučení na git cleanup,
- generátor nemá autoritativní resolver nejnovějšího TVBCP/handoffu ani
  klasifikaci zastaralého agregovaného stavu.

Cílové chování generátoru:

1. Oddělit tři části výsledku:
   - provozní předpoklady,
   - nejvýše pět strategických směrů,
   - informační příloha registru.
2. Používat pořadí zdrojů pravdy z oddílu 2 tohoto dokumentu.
3. Znovu použít existující kanonické vazby pracovních proudů a jejich
   strukturované handoff/TVBCP údaje; nevytvářet druhý katalog.
4. ACTIVE_PROJECTS.md používat jako fallback a agregovaný registr, ne jako
   automaticky nejčerstvější pravdu.
5. Pokud je novější kanonický zdroj v rozporu s agregovaným řádkem:
   - doporučení založit na novějším ověřeném stavu,
   - rozpor uvést jako „paměť vyžaduje narovnání“,
   - starý další krok nevydávat za současný.
6. Rozlišovat Git stavy:
   - dirty strom,
   - clean aligned,
   - clean local ahead / GitHub batch pending,
   - remote ahead,
   - divergence,
   - neověřeno.
7. Clean local ahead nesmí doporučovat dělení rozpracovaných změn; má uvést
   počet hotových commitů čekajících na denní balíček.
8. Počítat pouze skutečně aktivní připomínky. Historické nebo překryté záznamy
   mohou být v příloze, ale nesmějí zvyšovat hlavní alarm.
9. Hotový projekt bez okamžité akce nesmí vytlačit otevřený systémový směr jen
   proto, že má prioritu 1.
10. Strategický shortlist hodnotit podle:
    - provozního blockeru,
    - explicitní priority,
    - systémového dopadu,
    - ověřeného otevřeného kroku,
    - čerstvosti autoritativního zdroje,
    - závislosti dalších projektů na daném kroku.
11. Pokud důkazy nestačí, generátor nesmí hádat; vrátí „neověřeno“ a nejmenší
    read-only krok k doplnění důkazu.
12. Quick režim má být krátký rozhodovací itinerář. Full režim může obsahovat
    úplný registr až jako přílohu.

Nejmenší implementační pořadí:

Fáze A - opravit provozní klasifikaci:

- zavést explicitní Git state místo hledání slova „ahead“,
- přidat test clean local ahead -> GitHub batch pending,
- zachovat dirty/divergence fail-closed chování.

Fáze B - aktuálnost zdrojů:

- doplnit strukturovaný resolver kanonického workstreamu,
- načíst nejnovější současný blok TVBCP/handoffu, pokud existuje,
- označit rozpor s ACTIVE_PROJECTS.md,
- přidat regresní scénáře R2-Adam a Rodinný kalendář se zastaralým agregátem.

Fáze C - užitečné doporučení:

- odstranit mechanickou volbu priority_1[0],
- generovat nejvýše pět seřazených směrů,
- oddělit hotové/maintenance položky od skutečně otevřených,
- v quick režimu skrýt dlouhý katalog.

Fáze D - připomínky a výstup:

- rozlišit aktivní a historické [PRIPOMENOUT],
- ukázat zdroj a stáří důkazu každého doporučeného směru,
- uvést rozpory paměti jako samostatný úkol k narovnání.

Povinné testy:

- clean main ahead není dirty cleanup,
- dirty strom zůstává provozní blocker,
- divergence zůstává fail-closed,
- novější TVBCP/handoff přebije zastaralý agregovaný další krok,
- R2-Adam není označen „před implementací“,
- Rodinný kalendář nedostane starý aktivační krok,
- historické připomínky nezahlcují aktivní počet,
- quick report obsahuje nejvýše pět strategických směrů,
- full report zachová bezpečnou přílohu registru,
- report nečte ani nevypisuje private obsah,
- save režim nadále nepřepisuje starší report stejného dne.

Akceptační kritérium:

Po opravě musí nový audit nad aktuálním stavem rozpoznat:

- čistý GitHub batch pending,
- aktuální a ověřenou zálohu,
- Cockpit Dietu D0-D3 jako uzavřený směr, nikoli nový úkol,
- pravdivou paměť P0-P6 jako uzavřený směr s poctivým
  `aggregate_unverified` fallbackem,
- úplný tok e-mail -> private vault -> R2 TXT jako první věcný směr,
- R2 přejímku jako navazující směr,
- automatizaci sovy jako živý Pages workflow bez zápisu do `main`,
- žádný návrat starého VoiceBridge, starého kalendářového kroku nebo tvrzení,
  že R2-Adam ještě nebyl implementován.
