UŽIVATELSKÝ VÝSLEDEK
Práce / Probíhá / Doplnit pokyn do této práce obsahuje samostatný editor,
tlačítko Doplnit tento tah, stav účtenky a Pouze ověřit doplnění. Hlavní editor
nového zadání zůstává oddělený; nedochází k automatickému předání draftu do něj.
UI rozlišuje přijetí do původního tahu, odmítnutí a neověřené doručení. Přijetí
není Hotovo, dokončený výsledek ani nová autorizace. Historie má posledních
16 účtenek. Text/HTML se vykresluje jen jako text, ne jako aktivní obsah.

Při odmítnutí, nejistotě nebo doběhnutí tahu se text zachová. Přijatý text se
vyčistí jen tehdy, pokud uživatel mezitím nenapsal jiný. Při přepnutí kontextu
zůstane draft označený jako text jiné práce a nejde bez úpravy automaticky
odeslat do nového cíle. Polling zachová fokus, výběr, hlavní draft, starší chat
i předčítání. Accepted/pending/unverified práce se nezaměňují za skončený tah.

KONTRAKT A VLASTNICTVÍ
Backendový command_id je ha06-<operation_id>-<32 hex nonce>. Je tak trvale
svázaný i se svým rodičem; nejde zkopírovat ID a zaměnit cíl. Příkaz obsahuje
jen operation_id, command_id, expectedTurnId, text a serverem ověřený workstream.
HTTP navíc vyžaduje confirmed=true. Neznámá pole včetně write_intent/model/
sandboxPolicy/cwd jsou odmítnutá. Text je nejvýše 4000 znaků.

Před odesláním se znovu ověří aktivní projekt, vlastník controlleru/workeru,
neměnný původní scope uložený v handle, přesný turn ID, běžící modelový stav,
platný turn/started a živé původní spojení. Hub guard ověří identitu klienta,
thread, connection_generation, původní aktivní client_message_id i nezměněný
model/effort/sandbox/approval kontext. Původní profilový operation lock zůstává
držený původním workerem; doplnění nezískává jiný profil nebo nový workspace.
Stale/cizí wire event nezmění ani interní příznak turn_started/turn_completed,
pokud jej původní store skutečně nepřijal. Guard se znovu provede před RPC.

Jediný wire krok je turn/steer na původním klientovi s threadId, expectedTurnId,
clientUserMessageId a jedním textovým input. Není modelový/sandboxový override,
turn/start, nové vlákno, reconnect nebo náhradní klient. Text připomíná původní
DEVELOPMENT_CONTROL a nevydává se za souhlas s publikací nebo širšími právy.
Přijetí vyžaduje RPC result.turnId shodné s očekávaným tahem. Strukturovaná RPC
chyba je odmítnutí; chybné/cizí ACK, timeout nebo výpadek zůstává neověřený.
Raw zprávy serveru ani soukromé chyby se do účtenky/logu/UI nepřebírají.

POTVRZENÍ PŮVODNÍHO ZADÁNÍ
Nový connection-local ledger je pro append výslovně opt-in. Před RPC rezervuje
jen přesné autorizované command IDs; nejde o důkaz jejich přijetí. Původní
send_text stále vyžaduje právě jednu původní userMessage, turn/started,
konečnou odpověď a completed. Další user položky smějí patřit jen rezervovaným
doplněním a nesmějí se zdvojit. Chybějící/zdvojený původní input nebo cizí ID
nedostane kladnou účtenku. Po skončení/selhání se kontext uzavře ve finally.
Bez opt-in nejde append rezervovat. ScienceNews/ostatní one-turn guardy
zůstávají v cestě a nedostávají obecnou výjimku na více uživatelských vstupů.

Původní práce může mít potvrzený výsledek, zatímco jednotlivé doplnění zůstane
neověřené: rezervovaný ID znamená autorizovaný vstup, ne potvrzené RPC. Tyto
dvě účtenky se neslévají a rodičovské dokončení nezmění unknown na accepted.
Závod doběhnutí modelu a odpovědi steer řeší přesný serverový expectedTurnId;
pozdní výsledek doplnění se ukládá odděleně bez přepsání terminálního rodiče.

TRVALÝ JOURNAL A BEZ REPLAY
Před jediným RPC vznikne atomický pending command v private journalu. V rodiči
se trvale označí jeho inicializace před dispatch; pozdější chybějící/prázdný
journal je nedostupný zdroj, nikoli nový požadavek. Otisk zahrnuje celý přesný
normalizovaný příkaz a workstream. Stejné ID se stejným otiskem vrací původní
účtenku bez RPC a zápisu; jiný text/tah/rodič pod stejným ID je konflikt.

64 identit na rodiče, 16 posledních textů; starší accepted/rejected účtenky
zůstanou jako malé identity/otisky bez duplicitního textu. Nevyužívá se krátká
obecná cache repository. Při pending/unverified je další doplnění blokované.
Accepted/rejected dovolí další až po novém výslovném stisku uživatele a s novým
ID; žádné z toho není automatický retry. Reader nevytváří journal ani worker.

Živý pending má vlastníka v původním HTTP request vláknu. Při pádu/změně
serveru nebo ztrátě volajícího bez hotové účtenky se čte jako unverified, ne jako
nově odeslatelný příkaz. HTTP disconnect nezruší již prováděné RPC; druhý klient
může pouze číst stejnou účtenku. Modelový RPC neprobíhá pod controller/journal
zámkem; původní delivery reader, terminal callback a ostatní čtení mohou doběhnout.
Selhání uložení odpovědi po RPC nepovolí další provedení, ani při stejné identitě.

API A UI ČTENÍ
POST /api/human-adam/work/steer vrací doménovou účtenku; HTTP200/ok samo o sobě
neznamená accepted. Rozhoduje command.state a accepted_into_turn. Známé odmítnutí
před RPC je výslovně dispatch_performed=false. GET /api/human-adam/work/command
čte jedinou účtenku podle workstream/operation/command ID a má no-store.
Duplicitní query, cizí origin, chybějící potvrzení a přidané override jsou odmítnuté.
Obě operace jsou v capability registry; mutační cesta i v Cockpit action inventáři.

UI se zapne jen z výslovné work_protocol command_protocol=1 a pevných místních
cest. Referenci ID/expectedTurn ukládá před POST, ne text draftu. POST deadline
10 s při ztrátě odpovědi přejde pouze na GET stejného ID; čtení má deadline 5 s,
omezený backoff a žádný souběžný fetch. Chybějící účtenka není důkaz neodeslání.
Accepted/rejected/unverified automatické čtení ukončí; pending se dál dohledává.
Ověřit doplnění je jen GET. Změna scope/command generace zruší staré čtení;
jeho pozdní odpověď ani chyba nepřebije novější příkaz. Pageshow/reload může
obnovit pouze čtení. Text z odmítnuté/neověřené již odeslané účtenky lze obnovit
jako draft; neodeslaný draft se na server nově neukládá.

VERZE A OTEVŘENÉ HRANICE
Primární reference OpenAI Docs:
https://learn.chatgpt.com/docs/app-server#steer-an-active-turn
Offline existující CLI0.167.0 schema TurnSteerParams/Response potvrzuje
clientUserMessageId, expectedTurnId a result.turnId. Append klient používá
konzervativní místní korelační mez peer>=0.167.0; není to tvrzení o vendorové
nedostupnosti turn/steer ve starších verzích. Základní minimum0.163.0 ostatních
funkcí se nemění. Starší/neznámý peer nedostane spekulativní RPC ani fallback.
Živá podpora metody, reálné user-item echo a fyzická přejímka nebyly sondovány.

Dosavadní striktní lokální fallback codex_delivery_recovery pro vícenásobné
user_message není rozvolněný. Při výpadku skutečného spojení po steerech může
rodič zůstat delivery_unknown, i když se později ukáže finální lokální záznam.
Neznámý výsledek se tím nepřemění na další start. Rozšíření takové přejímky by
muselo doložit přesné původní a autorizované command ID; není nahrazené odhadem.
Browserový reload při běžícím serverovém workeru dál sleduje stejnou práci.
